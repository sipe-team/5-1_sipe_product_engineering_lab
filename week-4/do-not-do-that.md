# 4주차 PRD: 린다이어트 "후기/팁" 탭 콘텐츠 활성화 (기록 데이터의 C2C 재활용)

> **한 줄 요약**: GNB "후기/팁" 탭을 회사 블로그·광고 유튜브가 채우던 자리에서, 유저가 쓴 콘텐츠와 기록 데이터 기반 정보가 도는 자리로 바꾼다. 지금 탭은 사실상 100% 톱다운이다.

## 분석 대상

- **서비스**: 린다이어트 (자사 B2B2C 한약 다이어트 앱)
- **선정한 페인포인트**: 기록 데이터가 사용자 → 원장 방향으로만 흐르고, 사용자 쪽으로 되돌아오는 통로가 없다. 그 결과가 지금의 "후기/팁" 탭이다.

### 3주차 검증과의 연결

3주차에서 "AI 칼로리 대기 시간"을 검증했더니 임팩트가 낮았다(ICE 36). 대신 그 과정에서 **기록 데이터(+31pp 식사기록 품질, +12% 원장 차트 열람)가 사용자 → 원장 방향으로만 흐르고 사용자에게는 돌아오지 않는다**는 인사이트를 얻었다.

---

## 1. 배경 및 문제 정의 (Why)

### 문제 상황

린다이어트 GNB 5개 중 하나인 "후기/팁" 탭의 하위 카테고리:

| 카테고리        | 생산자      | 사용자 관점 |
| --------------- | ----------- | ----------- |
| 전체글          | 운영팀 통합 | 메타 피드   |
| 실제 후기       | 운영팀      | 톱다운      |
| 한의사 이야기   | 회사        | 톱다운      |
| 연구 일지       | 운영팀      | 톱다운      |
| 다이어트 궁금증 | 운영팀      | 톱다운      |
| 린다이어트팀    | 운영팀      | 톱다운      |

6개 카테고리 전부 운영팀이 쓴다. 이름이 "실제 후기"인 것조차 유저가 쓴 글이 아니라 운영팀이 유저 후기처럼 쓴 거다. 유저가 직접 쓴 글은 하나도 없다. "후기/팁"이라는 이름과 다르게, 사실상 회사의 방송 채널이다.

### 영향받는 사용자

친구 소개로 한의원에 갔다가, 원내 데스크 안내를 받고 앱을 설치한 **40/50대 여성 신규 사용자**.

### 근거

- 앱스토어 리뷰 2,215개 중 "후기/팁 탭 도움 안 된다"는 직접 언급은 없다. 불만으로 올라올 만큼의 기대치 자체가 없는 상태.
- 탭 체류·재방문을 볼 수 있는 이벤트 자체가 거의 심어져 있지 않다. 여태 린다팀의 관심사가 아니었다는 뜻.
- GNB 5개 중 1개라는 비싼 자리를 주고도 올라오는 콘텐츠는 방송 톤. 전략과 실제가 어긋나 있다.

### 방치하면

- GNB 자리 하나를 계속 낭비
- "기록만 하는 앱"이라는 인상이 굳어짐 → 프로그램 이탈로 이어짐
- 기록 데이터가 유저 쪽으로 돌아오는 루프가 영영 안 생김

## 2. 목표와 성공 지표 (What + KPI)

### 목표

> "후기/팁" 탭을 회사 방송 채널에서 유저 참여 창구로 바꾼다. 기록 데이터가 앱 안에서 유저 → 유저 방향으로 한 바퀴 도는 첫 씨앗을 심는다.

### KPI

| 지표                  | 카테고리   | 목표  |
| --------------------- | ---------- | ----- |
| 탭 평균 체류 시간     | Engagement | ~90초 |
| 탭 D7 재방문율        | Retention  | +15pp |
| 신규 1주 내 첫 진입률 | Adoption   | +20pp |

**핵심 지표**: 체류 시간. 그냥 잠깐 열었다가 나간 경우를 걸러내려고 D7 재방문율을 같이 본다.

**베이스라인**: 지금은 탭 체류 이벤트 자체가 없어서, MVP 만들면서 같이 심어야 한다.

## 3. 사용자 경험 변화 (Before → After)

**페르소나**: 김영자씨.., 52세, 카페 자영업. 친구 소개로 한의원에 갔다가 앱 설치.

### Before

"후기/팁" 탭을 열어본다 → 상단에 한의사 칼럼·연구 일지·FAQ → "대사" 같은 단어에서 막혀서 탭을 나간다 → 이후 3개월간 다시 안 연다.

### After (수집 플로우가 돌기 시작한 뒤)

"후기/팁" 탭을 열어본다 → 상단에 **같은 시기 시작한 N명·감량 구간 정보** + **비슷한 나이대 다른 유저가 쓴 후기** → 내려가면서 기존 카테고리도 본다 → 한 달 뒤 주 2~3회 들어오고, 한 달 반 뒤 본인도 앱에서 뜬 작성 프롬프트로 후기 한 줄을 남긴다.

> _카테고리 문구·섹션 이름은 예시. 실제 UI 라벨은 UX 라이팅 단계에서 결정. MVP 직후에는 유저 후기가 아직 수집 중이라 데이터 카테고리부터 뜨고, 시드 후기가 모이면서 UGC가 순차적으로 채워진다._

## 4. 솔루션 접근법 (How 개괄)

### 3개 축

1. **유저가 쓴 콘텐츠 (UGC 0→1)**
   - 지금 탭에 유저 후기가 하나도 없어서 0부터 시작해야 한다
   - 앱 안에 후기 작성 프롬프트를 두고, 프로그램 N주차 시점에 띄운다
   - 초기 시드는 운영팀·CS팀이 유저에게 직접 요청해서 확보하는 경로도 열어둔다
   - 모수가 쌓이면 나이·시작 시점 기준으로 자동 큐레이션으로 넘어간다

2. **기록 데이터 기반 집단 정보**
   - 같은 시기 시작한 동료 수·감량 구간 같은 집단 통계를 카테고리로 보여준다
   - 프라이버시 가드레일: N≥20 / 구간화 / 고지문 / 유저 토글
   - 유저 후기가 쌓이기 전에는 이 카테고리가 탭 상단의 주 콘텐츠 역할을 한다

3. **유저 간 상호작용 씨앗 (V2 이후)**
   - 공감 버튼 → 댓글 → 그룹 피드 순으로 단계적으로 늘려간다
   - MVP에는 안 넣지만, 나중에 올릴 수 있도록 초기 데이터 스키마 단계에서 감안한다

### 기술 고려사항

- **UGC 수집 플로우**: 작성 프롬프트 트리거, 작성 UI, 작성 후 집계 파이프라인
- **모더레이션**: 처음엔 운영팀 수동 리뷰 + 유저 신고 버튼
- **측정 인프라**: 탭 체류·클릭·재방문·후기 작성 이벤트 같이 심기
- **A/B 테스트**: 신규와 기존 사용자 분리

## 5. ICE Score

| 후보  | 설명                                                                          |   I |   C |   E | ICE | 판단                             |
| ----- | ----------------------------------------------------------------------------- | --: | --: | --: | --: | -------------------------------- |
| **A** | 유저 카테고리 즉시 노출 + UGC 수집 플로우 도입 (시드 확보 후 단계적 UGC 노출) |   8 |   6 |   4 | 192 | **채택**                         |
| B     | 유저 카테고리만 먼저 (UGC는 V1로)                                             |   6 |   7 |   7 | 294 | 축소 시 fallback                 |
| C     | UGC 수집 플로우만 (데이터 카테고리는 V1)                                      |   6 |   5 |   5 | 150 | 보류                             |
| D     | 공감·댓글 반응 기능                                                           |   7 |   5 |   3 | 105 | V2                               |
| E     | 후기 작성 인센티브 도입                                                       |   6 |   5 |   6 | 180 | V1에서 검토 (UGC 수집률 부진 시) |
| F     | AI 대기 시간 개선                                                             |   4 |   3 |   3 |  36 | 보류 (3주차 재평가)              |
| G     | 탭 전면 리뉴얼                                                                |   9 |   5 |   2 |  90 | V3                               |

### 선택 근거

점수만 보면 B(294)가 A(192)보다 높지만 A로 간다. B는 "데이터 카테고리만 보여줘도 체류가 움직이는가"라는 좁은 질문에만 답하고, A는 "데이터와 유저 후기가 함께 있을 때 작동하는가"라는 이번 PRD의 진짜 질문에 답한다. 린다이어트 탭에 UGC가 0%인 상황에서는, 수집 플로우를 만드는 작업 자체가 이 PRD가 가려는 방향의 핵심 실험이다.

리소스가 정말 빠듯하거나 UGC 수집 플로우 설계가 막히면 **B로 축소**. 데이터 카테고리만 먼저 내고 UGC 수집은 V1으로 미룬다.

**D (인센티브)**: 처음에는 인센티브 없이 프롬프트만으로 시작하되, 2주간 수집률이 기대 이하면 V1에서 바로 도입한다.

## 6. 범위와 우선순위 (Scope)

| 범위             | 내용                                                                                                                                                                                                                                          | 우선순위 층위         |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| **MVP**          | ① 집단 통계 카테고리 1개(동료 수 or 감량 구간) 즉시 노출<br>② UGC 수집 플로우 도입 (앱 내 후기 작성 프롬프트 + 작성 UI + 집계 파이프라인)<br>③ 시드 후기 확보 후 UGC 카테고리 단계적 노출<br>④ 탭 체류·클릭·재방문·후기 작성 이벤트 같이 심기 | Must                  |
| **V1**           | 집단 통계 카테고리 2개로 확장. UGC 큐레이션 다듬기. 통계 참여 토글. 필요하면 인센티브 도입                                                                                                                                                    | Should                |
| **V2**           | 후기 공감 버튼. 반응 카운트                                                                                                                                                                                                                   | Could (커뮤니티 씨드) |
| **V3**           | 댓글·답글. 기간 기반 그룹 피드. 탭 전면 리뉴얼. 원장 B2B 확장                                                                                                                                                                                 | Could (장기)          |
| **Out of Scope** | 광고 유튜버 콘텐츠 즉시 제거, AI 대기 시간, 홈 영양소 노출, 탭 이름 변경, 본격 커뮤니티 기능                                                                                                                                                  | Won't                 |

**MVP가 4개인 이유**: 수집 채널·노출 채널·측정 인프라가 모두 같이 돌아야 이 PRD의 가설을 확인할 수 있다. 하나라도 빠지면 "이게 됐는지"를 판단할 방법이 없다.

## 7. 리스크

### 1. 프라이버시 역추론 (법률·데이터팀 우려)

- **시나리오**: 모수가 작을 때 감량 구간을 보여주면 역추론 가능. 사용자가 "내 기록이 나오는 거 아닌가?" 하는 순간 기록 자체를 안 하게 된다. 핵심 루프가 무너진다.
- **완화**: N≥20 / 구간화 / 고지문 / 참여 토글 / 법률팀 사전 리뷰 / 데이터팀 기술 감수

### 2. UGC 수집 실패 (가장 큰 불확실성)

- **시나리오**: 수집 플로우를 만들어도 40/50대 여성이 후기를 안 쓰면 이 가설을 확인할 방법이 없다. UGC 카테고리가 영영 빈 채로 남는다.
- **완화**:
  - 초기 시드는 운영팀·CS팀이 한의원 방문 때 직접 요청으로 확보
  - 2주간 수집률 모니터링하고, 기대 이하면 V1에서 인센티브(E) 바로 도입
  - 프롬프트 트리거 시점과 문구를 A/B로 조정
  - 최악의 경우 B안(데이터 카테고리만)으로 축소

### 3. 집단 수치·유저 후기가 사용자에게 압박이 되는 경우

- **시나리오**: 평균보다 낮은 자기를 보고 좌절해서 기록을 접는다. 40/50대는 이런 비교에 특히 민감할 수 있다.
- **완화**: 숫자 대신 구간 노출 / 시작 시점 기준으로 비교 / 성공 사례만 뽑지 않기 / 기록 중단율을 가드 지표로 모니터링

### 4. UGC 편향·조작 (수집 시작 후 나타남)

- **시나리오**: 긍정 후기만 올라오면 광고처럼 읽힌다. 초기 시드로 운영팀이 받아온 후기도 특정 성향으로 기울 수 있다.
- **완화**: 세그먼트 필터만 적용(품질 점수 매기지 않음) / 부정 후기도 허용하는 정책 / 초기 시드 요청 시 가이드 문구는 중립 / 유저 신고 버튼은 MVP에 포함

### 5. 운영팀 역할 변화에 대한 내부 저항

- **시나리오**: 지금 운영팀이 "실제 후기"까지 포함한 6개 카테고리를 직접 쓰고 있는데, 일부가 UGC로 대체되면 "우리 역할이 줄어드는 거 아니냐"는 이야기가 나올 수 있다.
- **완화**: 기존 카테고리는 삭제하지 않는다 / 운영팀 역할을 "작성"에서 "모더레이션·시드 요청·큐레이션"으로 재정의 / 사전에 같이 읽는 자리 만들기

### 6. 신규 vs 기존 사용자 반응 차이

- **시나리오**: 기존 사용자는 새 섹션을 방해물로 느낄 수 있다.
- **완화**: A/B 테스트에서 신규/기존 분리 / 기존 사용자에게는 기본 접힌 상태도 검토

## 8. 열린 질문

- UGC 작성 프롬프트 트리거 시점 — 프로그램 며칠·몇 주차가 적당한지 (사용자 인터뷰 필요)
- 초기 시드 후기 확보 방식 — 프롬프트만 vs 운영팀·CS팀 개별 요청 vs 인센티브
- UGC 수집률이 낮을 때 V1에서 인센티브 도입하는 기준선
- 프라이버시 최소 모수 N=20이 적절한지 (법률팀 검토)
- 통계 참여 토글 기본값 ON/OFF
- 세그먼트 기준 ±5세/±2주가 유저 체감상 "비슷함"에 맞는지 (사용자 인터뷰)
- 페르소나(40/50대 여성)가 맞는지 — 실제 연령대 분포 확인
- 체류 시간이 진짜 학습·교감과 연결되는지 검증
- 부정·실패 후기 허용 비율을 어떻게 잡을지
- 후기 모더레이션 책임 부서 — 운영팀·CS팀 중 어디
- 실제 UI 라벨 결정 주체
- 측정 인프라: MVP 선행 vs 병행

> 이 글을 읽으면서 우리 회사 작업과 계속 비교하게 됐다. 특히 **Must Have / Should Have / Could Have** 개념이 기억에 남았다. 우리 팀은 MVP 단위를 잘게 깎는 작업은 이미 하고 있는데, 여기에 "지금 만들 것 / 곧 해야 할 것 / 있으면 좋을 것" 층위가 기획 리뷰 싱크 단계에서 명시적으로 공유되면, 바꾸기 큰 품이 드는 **DB·인프라·아키텍처 설계**를 할 때 확장 감을 안고 설계할 수 있겠다는 생각이 들었다. 큰 설계 결정을 실제로 지는 개발자가 프로덕트에 관심을 가졌을 때에야 꺼낼 수 있는 관점이라는 걸 쓰면서 느꼈다. 이번 주 목요일 데일리 스크럼에 팀에 공유할 예정이다.
>
> 이 PRD 섹션 6의 MVP / V1 / V2 / V3 / Out of Scope 구조는 Must / Should / Could Have를 시간축으로 풀어낸 것이다. MVP는 "데이터 카테고리 1개 + UGC 수집 플로우 도입"의 병행 구성으로 좁히되, V2 커뮤니티 씨드와 V3 전면 리뉴얼로 확장 경로를 미리 열어두었다.
>
> 글에서 "사용자를 분명히 정의하고, 그 사용자가 어떤 어려움을 겪는지 기술하라"는 대목도 기억에 남았다. 우리 팀은 이미 기능 리뷰 때 **페르소나에 이입하는 리뷰**를 잘 하고 있다는 걸 이 글을 보면서 재확인했다. 이번 PRD의 Before/After 섹션에도 김영자 님이라는 한 사람을 끝까지 끌고 가는 방식으로 시나리오를 구성했다.

## (자사 서비스) 실행 관점

### 리소스

Mobile 1 / BE 1 / 디자이너 1 / 기획 1. 전원 다른 프로젝트랑 병렬로 돌고 있어서 MVP는 일부 시간 할당 수준으로 맞춰야 한다.

### 이해관계자

| 역할       | 반응                            | 대응                                                                    |
| ---------- | ------------------------------- | ----------------------------------------------------------------------- |
| PM         | 찬성 (추측....)                 | 내부 스폰서 확보                                                        |
| 법률팀     | 우려 (가명처리 + UGC 노출 책임) | 가드레일 설계 단계부터 명시, 사전 리뷰                                  |
| 데이터팀   | 우려 (역추론 가능성)            | 기술 감수, K-anonymity 논의                                             |
| 운영팀     | 우려 (역할 변화)                | 작성에서 모더레이션·시드 요청·큐레이션으로 재정의. 기존 카테고리는 유지 |
| CS팀       | 업무 증가 우려                  | MVP는 자동 필터 + 신고 버튼 + 수동 시드 요청 수준                       |
| 원장 (B2B) | 중립                            | V3에서 코칭 도구 확장 가능성 공유                                       |

### 제안 계획

- **타이밍**: 2분기 계획 논의 시점
- **1차 공유**: PM에게 먼저
- **2차**: 법률·데이터·운영·CS팀에 개별 리뷰
- **공식 제안**: 위 피드백 반영 후 팀 전체 공유
- **백업**: 이번 분기에 리소스가 안 되면 2분기 논의의 재료로만 쓴다
