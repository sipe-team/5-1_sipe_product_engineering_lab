# 4주차: PRD — 비로그인 구매 전환 플로우 개선: "회원가입 후 원래 포스트로 돌아가기"

> **한 줄 요약**: 비로그인 사용자가 유료 포스트 구매를 시도한 뒤 회원가입을 완료하면 홈 화면으로 빠져 원래 포스트를 찾을 수 없는 문제를, 가입/인증 완료 후 자동으로 해당 포스트로 복귀시키는 플로우로 개선한다.

## 분석 대상

- **서비스**: 포스타입(Postype) — iOS/Android 앱 및 모바일 웹
- **선정한 페인포인트**: 비로그인 상태에서 유료 글 구매 시도 → 회원가입/이메일 인증 → 홈으로 리다이렉트되어 원래 포스트를 다시 찾을 수 없음 → 구매 전환 실패 및 신규 유저 이탈

---

## 1. 배경 및 문제 정의 (Why)

### 문제 상황

포스타입에서 신규 사용자가 유료 콘텐츠를 처음 구매하기까지의 여정은 다음과 같다:

1. 트위터(X) 등 외부 SNS에서 작가의 포스타입 링크를 클릭
2. 비로그인 상태로 포스트 미리보기 확인 → 유료 부분을 읽기 위해 "구매" 클릭
3. 로그인/회원가입 화면으로 이동
4. 회원가입 진행 (이메일 입력 → 이메일 인증 필요)
5. **이메일 인증 완료 후 홈 화면으로 이동됨**
6. 원래 보려던 포스트의 URL이나 제목을 기억하지 못함
7. 포스트를 다시 찾지 못하고 이탈

핵심 문제는 **5번 단계**에서 발생한다. 회원가입과 이메일 인증이라는 다단계 프로세스를 거치는 동안 원래 포스트의 컨텍스트(URL)가 유실되어, 가입을 완료한 사용자가 구매 의향이 있던 포스트로 복귀할 수 없다.

### 영향받는 사용자

- **직접 영향**: 비로그인 상태에서 유료 포스트 구매를 처음 시도하는 신규 사용자 전원
- **간접 영향**: 해당 포스트를 판매하는 크리에이터 (구매 전환율 저하로 인한 수익 감소)
- **규모 추정**: 포스타입은 매월 약 400만 건의 콘텐츠 거래가 발생하며, 외부 SNS(특히 트위터)에서의 유입이 핵심 채널이다. 외부 유입 사용자 중 비로그인 비율을 보수적으로 20%만 잡아도, 월 수십만 건의 잠재 구매 시도가 이 플로우를 거칠 수 있다.

### 근거

**앱 스토어 리뷰 분석(2024~2026)에서의 간접 근거:**

- App Store(3.5점/5), Google Play(3.6점/5)의 낮은 평점
- "로딩이 느리고 웹이 더 빠르다"는 리뷰에서 앱↔웹 전환 과정의 UX 결함이 반복적으로 지적됨
- 네이버 로그인 시 에러 후 백지 상태가 되는 등, 인증 플로우에서의 컨텍스트 유실 문제가 산발적으로 보고됨
- 나무위키에서 "앱에서 모바일 웹으로 전환 시 다른 사용자 계정으로 전환되는 사고"가 기록 — 인증 플로우의 상태 관리가 취약함을 시사

**업데이트 노트 분석(2025.10~2026.04)에서의 근거:**

- 25회 업데이트 중 76%가 "서비스 안정성과 앱 성능을 개선했어요"라는 동일 문구
- 신규 기능 4건은 전부 캐릭터톡·오픈 채널·프리미엄 관련 — 회원가입/구매 전환 플로우 개선은 한 번도 언급되지 않음
- 사용자가 요청한 책갈피, 이어보기 등 "원래 위치로 돌아가기" 계열 기능이 2년간 방치

**기술 블로그 분석에서의 근거:**

- 포스타입 백엔드 팀은 SpringBoot 기반 API 서버를 운영하며, AWS 인프라 최적화에는 체계적으로 투자 중

**이 문제가 스토어 리뷰에 직접 등장하지 않는 이유:**

- 이 시나리오의 사용자는 "가입을 막 완료한 신규 유저"이므로 리뷰를 남길 만큼의 플랫폼 관여도가 형성되기 전에 이탈
- 전형적인 "조용한 이탈(Silent Drop-off)" 패턴 — 분노가 아닌 귀찮음으로 이탈하므로 데이터에 잡히지 않음

### 방치하면 생기는 비즈니스 영향

1. **신규 유저 첫 구매 전환율(Activation Rate) 저하**: 가입까지 했는데 구매를 못 한 사용자는 "다음에 해야지" → 대부분 돌아오지 않음
2. **크리에이터 수익 감소**: 외부 SNS에서 유입된 잠재 구매자가 전환되지 않으면 크리에이터의 포스타입 수익이 줄고, 이는 크리에이터 이탈로 이어질 수 있음
3. **수수료 인상 반감 악화**: 2025년 3월 수수료를 13%+발견수수료 17%로 인상한 상황에서, 전환율까지 낮으면 크리에이터에게 "수수료는 올리고 구매는 안 되게 만든다"는 이중 불만 형성
4. **캐릭터톡 등 신규 기능의 효과 제한**: AI 캐릭터톡으로 신규 유입을 늘려도, 유료 콘텐츠 구매 퍼널이 막혀 있으면 매출로 전환되지 않음

## 2. 목표와 성공 지표 (What + KPI)

### 목표 (Goal)

> 비로그인 사용자가 유료 포스트 구매를 위해 회원가입을 완료한 후, 추가 탐색 없이 해당 포스트로 즉시 복귀하여 구매를 완료할 수 있는 상태를 만든다.

### 성공 지표 (KPI)

| 지표                                    | HEART 카테고리 | 현재(추정)                     | 목표     |
| --------------------------------------- | -------------- | ------------------------------ | -------- |
| 회원가입 후 5분 내 첫 구매 완료율       | Task Success   | ~10~15% (추정)                 | 40% 이상 |
| 회원가입 → 포스트 복귀율                | Task Success   | ~0% (홈으로 빠짐)              | 90% 이상 |
| 비로그인 유입 → 가입 → 구매 퍼널 완주율 | Adoption       | 측정 불가(현재 추적 미비 추정) | 30% 이상 |

**핵심 지표**: **회원가입 후 5분 내 첫 구매 완료율**

이 지표가 핵심인 이유는, "포스트 복귀" 자체는 수단이고 최종 목적은 "구매 완료"이기 때문이다. 사용자가 포스트로 돌아갔더라도 포인트 충전 등 다음 단계에서 이탈할 수 있으므로, 최종 전환(구매 완료)까지 추적해야 실제 비즈니스 임팩트를 측정할 수 있다.

## 3. 사용자 경험 변화 (Before → After)

### Before (현재)

> 대학생 민지(22)는 트위터에서 좋아하는 일러스트 작가가 올린 포스타입 링크를 클릭했다. 작가의 유료 일러스트 모음이 3,000원에 판매되고 있었다. 미리보기 3장이 너무 마음에 들어 "구매하기"를 눌렀더니 로그인 화면이 나왔다. 포스타입 계정이 없어서 네이버로 회원가입을 진행했다. 이메일 인증 메일이 날아왔고, 메일 앱으로 이동해서 인증 링크를 클릭했다. 인증이 완료되자 포스타입 홈 화면이 떴다. "그 일러스트 어디 있었지?" 검색을 시도했지만 작가 닉네임을 정확히 기억하지 못했다. 트위터로 다시 가서 원래 트윗을 찾으려 했지만 타임라인이 이미 밀려 있었다. 결국 "나중에 찾아봐야지"라고 생각하고 앱을 닫았다. 그 "나중에"는 오지 않았다.

### After (개선 후)

> 민지는 동일하게 트위터에서 링크를 클릭하고, 유료 포스트를 보고 "구매하기"를 눌렀다. 로그인 화면에서 네이버로 회원가입을 진행했다. 이메일 인증 화면이 나왔고, 화면 중앙에 "인증 메일을 보냈어요. 메일함을 확인해주세요"라는 안내와 함께 **"인증 확인"** 버튼이 보였다. 민지는 메일 앱에서 인증 링크를 클릭한 뒤 다시 포스타입 앱으로 돌아와 "인증 확인" 버튼을 눌렀다. 버튼을 누르자 **아까 보고 있던 일러스트 모음 포스트로 바로 이동**되었다. 포인트 충전 후 3,000원을 결제하고 일러스트를 감상했다. 가입부터 구매까지 3분이 채 걸리지 않았다.

## 4. 솔루션 접근법 (How - 개괄)

### 접근 방식

> 비로그인 상태에서 구매를 시도한 시점의 포스트 URL을 세션/파라미터로 보존하여, 회원가입·이메일 인증 완료 후 해당 URL로 자동 리다이렉트한다.

### 핵심 아이디어

1. **returnURL 파라미터 전달**: 비로그인 사용자가 "구매하기"를 누른 시점에 현재 포스트 URL을 `returnURL` 파라미터로 로그인/회원가입 화면에 전달. 가입 완료 후 해당 URL로 리다이렉트.
2. **이메일 인증 대기 화면에 "인증 확인" 버튼 추가**: 현재는 이메일 인증 링크를 클릭하면 별도 브라우저 탭에서 인증이 완료되고 맥락이 끊김. "인증 확인" 버튼을 앱 내 대기 화면에 배치하여, 사용자가 메일 인증 후 앱으로 돌아와 버튼을 누르면 서버에 인증 상태를 확인(polling)하고, 성공 시 `returnURL`로 이동.
3. **인증 완료 딥링크 개선**: 이메일 인증 링크 클릭 시 웹이 아닌 앱으로 바로 복귀하는 딥링크(Universal Link / App Link) 적용. 딥링크에 `returnURL`을 포함시켜 앱 내에서 바로 해당 포스트로 이동.

### 기술적/디자인적 고려사항

- SpringBoot API 서버에 `returnURL` 파라미터를 회원가입 세션 전체에 걸쳐 전달하는 로직 추가 필요
- 이메일 인증 대기 화면에서의 polling 주기 설정 (너무 잦으면 서버 부하, 너무 드물면 UX 지연)
- 소셜 로그인(네이버/애플/구글) 경로에서도 returnURL이 유실되지 않도록 OAuth 콜백 처리 확인
- `returnURL` 파라미터의 보안: XSS/Open Redirect 방지를 위해 포스타입 도메인 내부 URL만 허용하는 화이트리스트 검증 필요
- 앱↔웹 전환 시 딥링크가 정상 작동하지 않는 엣지 케이스 처리 (특히 삼성 인터넷, 인앱 브라우저 등)

## 5. ICE Score

이번 문제를 해결할 수 있는 후보 아이디어를 비교한다. 각 항목은 1~10 스케일이며, ICE Score는 세 점수의 평균이다.

|       | 후보 아이디어                       | 설명                                                                                                                                                            | Impact | Confidence | Ease | ICE Score | 판단                   |
| ----- | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ | ---------- | ---- | --------- | ---------------------- |
| **A** | returnURL 세션 보존 + 자동 복귀     | 비로그인 시점 포스트 URL을 세션/파라미터로 보존하고, 가입·인증 완료 후 해당 URL로 자동 리다이렉트. 이메일 인증 대기 화면에 "인증 확인" 폴링 버튼 + 딥링크 포함. | 9      | 7          | 5    | **7.0**   | 채택                   |
| **B** | 게스트 체크아웃 (회원가입 deferral) | 회원가입을 뒤로 미루고 이메일·결제 정보만으로 즉시 구매 가능하게 함. 구매 완료 후 비밀번호 설정 안내.                                                           | 8      | 5          | 3    | **5.3**   | 보류                   |
| **C** | 인증 메일 링크에 포스트 ID embed    | 가입 후 받는 인증 이메일의 링크 URL 자체에 원래 포스트 정보(예: `?post_id=...`)를 담아, 메일 클릭 시 인증 처리 후 곧장 해당 포스트로 이동.                      | 7      | 8          | 7    | **7.3**   | V1 후보 (A의 부분집합) |
| **D** | 홈 화면 "최근 본 포스트" 배너       | 가입/인증 후 홈으로 이동했을 때, 가입 직전 보던 포스트로 돌아가는 배너를 상단에 노출. 쿠키/세션 기반.                                                           | 6      | 7          | 8    | **7.0**   | 보류 (Fallback UI)     |

### 선택한 아이디어 — A (returnURL 세션 보존 + 자동 복귀)

C가 평균 점수는 0.3 더 높지만 **A를 선택**했다. 이유는 다음과 같다:

- C는 "메일 클릭 → 웹 브라우저로 이동"하는 한 가지 경로만 커버한다. 사용자가 메일 인증 후 **앱으로 직접 돌아오는 경우**(현실적으로 모바일 사용자의 다수)에는 효과가 없다. A는 메일 클릭 경로와 앱 복귀 경로를 모두 커버한다.
- C는 사실상 A의 부분집합이므로, A를 단계적으로 출시하면서 1단계에 C의 효과를 자연스럽게 흡수할 수 있다.
- Impact 차이(9 vs 7)가 결정적이다. NSM(수익 크리에이터 수)에 직결되는 핵심 퍼널이라면, Ease가 다소 낮더라도 근본 해결책을 택하는 것이 ROI 관점에서 옳다.

### 선택하지 않은 아이디어

- **B (게스트 체크아웃)** — Impact는 높지만 포스타입의 포인트·멤버십·정산 구조 전체에 영향을 주는 구조 변경이다. 회원이 아닌 구매자에게 환불·문의·콘텐츠 재열람을 어떻게 제공할지에 대한 정책 설계부터 필요해 이번 스프린트 범위를 크게 벗어난다.
- **D (홈 화면 배너)** — Ease가 높은 빠른 패치지만, 이미 홈에 도달한 사용자가 한 번 더 클릭해야 하므로 전환율 개선 효과가 A에 비해 제한적이다. A의 1단계가 작동하지 않는 엣지 케이스(쿠키 차단, 시크릿 모드 등)의 **Fallback UI로만** 가치가 있어 V2에서 검토.

| **MVP (이번에 만들 것)** | • 모바일 웹 + 이메일 회원가입 경로의 returnURL 파라미터 전달 |

• 이메일 인증 링크 자체에 returnURL 포함 (위 표의 C안 효과 흡수)
• Open Redirect 방지: 포스타입 도메인 화이트리스트 검증
• 퍼널 단계별 이벤트 로깅 (비로그인 구매 클릭 → 가입 시작 → 인증 완료 → 포스트 복귀 → 구매 완료) |
| **V1 (다음 스프린트)** | • iOS / Android 딥링크(Universal Link / App Link) 적용
• 이메일 인증 대기 화면에 "인증 확인" 폴링 버튼 (3~5초 간격, 최대 30회)
• 소셜 로그인(네이버) OAuth 콜백 경로의 returnURL 보존 |
| **V2 (나중에)** | • 애플 / 구글 OAuth 콜백 경로의 returnURL 보존
• 홈 화면 "최근 본 포스트" Fallback 배너 (위 D안)
• 포인트 충전 → 복귀 → 구매까지 returnURL 체인 유지 |
| **Out of Scope** | • 게스트 체크아웃 (위 B안)
• 책갈피·이어보기 등 별도 신규 기능
• PC 웹 환경 최적화 (PC 비로그인 → 유료 구매 시도 비중 낮음)
• 외부 SNS(트위터)와의 별도 연동 API |

## 7. 리스크와 대안 (Risks)

### 리스크 1: Open Redirect 보안 취약점

- **시나리오**: 공격자가 returnURL 파라미터에 외부 피싱 사이트 URL을 주입한 가짜 포스타입 가입 링크를 배포. 사용자가 가입을 마치면 피싱 사이트로 자동 리다이렉트되어 계정 탈취·결제정보 유출로 이어짐.
- **완화**:
  - returnURL은 포스타입 도메인(`postype.com`, `www.postype.com`, `.postype.com`) 화이트리스트만 허용
  - 상대 경로(`/posts/...`) 우선 사용, 절대 URL은 도메인 검증 후에만 통과
  - 보안팀 사전 리뷰 + 자동화된 Open Redirect 테스트 케이스 추가

### 리스크 2: 딥링크 미작동 환경에서의 플로우 단절

- **시나리오**: 트위터·인스타그램 인앱 브라우저, 삼성 인터넷, 일부 안드로이드 메일 앱에서는 Universal Link / App Link가 작동하지 않아 사용자가 외부 브라우저로 빠지고 포스트로 돌아오지 못함. 가장 핵심 유입 채널인 트위터에서 가장 자주 발생할 수 있음.
- **완화**:
  - 딥링크 실패 시 모바일 웹 returnURL로 fallback (MVP에서 모바일 웹 경로를 먼저 만드는 이유)
  - 출시 전 트위터 인앱 브라우저, 삼성 인터넷, 카카오톡 인앱 브라우저 우선 QA
  - 인증 메일 본문에 "앱으로 돌아가기" + "웹에서 계속하기" 두 가지 링크 병행 제공

### 리스크 3: "인증 확인" 폴링 버튼이 오히려 혼란 유발

- **시나리오**: 사용자가 메일 인증을 하지 않은 채 "인증 확인" 버튼만 반복해서 누르거나, 버튼의 존재를 알아채지 못해 무한 대기. 또는 폴링 부하로 인증 서버 응답 지연.
- **완화**:
  - 백엔드 자동 감지(WebSocket 또는 5초 폴링)를 기본으로 하고, "인증 확인" 버튼은 보조 수단으로 배치
  - 버튼 카피를 "메일에서 인증 후 여기를 누르세요"처럼 행동 순서를 명시
  - 폴링은 클라이언트당 최대 30회(약 2~3분) 후 자동 중단, 이후엔 새로고침 안내
  - 인증 미완료 상태에서 버튼 클릭 시 "아직 메일 인증이 확인되지 않았어요" 명시적 피드백

## 8. 열린 질문 (Open Questions)

다음 항목은 본격 개발 착수 전 또는 출시 직후 검증이 필요하다.

- **베이스라인 측정**: PRD에 적은 "회원가입 후 5분 내 첫 구매 완료율 10~15%"는 추정값이다. MVP 출시 전에 실제 베이스라인을 측정해야 ICE의 Confidence를 6 → 8 이상으로 끌어올릴 수 있다.
- **트래픽 분포**: 비로그인 유입 중 외부 SNS 비중, 그중 트위터 인앱 브라우저 비중은? 인앱 브라우저 비중이 압도적이라면 V1의 딥링크 작업 우선순위가 더 올라간다.
- **가입 경로 비중**: 신규 가입자 중 이메일 가입 vs 소셜 로그인(네이버·애플·구글) 비중은? 소셜 로그인 비중이 50%를 넘는다면 OAuth 콜백 returnURL 보존을 V1이 아닌 MVP로 끌어올려야 한다.
- **포인트 충전 단계의 영향**: returnURL로 포스트에 복귀해도, 신규 유저는 포인트 잔액 0이라 충전 페이지로 다시 이동해야 한다. 이 추가 단계가 최종 구매 전환율을 얼마나 희석시키는가? 충전 → 복귀까지 returnURL 체인을 MVP에 포함시켜야 할지 검토 필요.
- **다른 결제 진입점과의 일관성**: 후원·팁·멤버십 가입 등 유료 포스트 구매 외 진입점도 동일한 비로그인 → 가입 → 컨텍스트 유실 문제를 가진다. 이번 작업의 returnURL 패턴을 그대로 확장 적용 가능한가, 아니면 진입점별 별도 설계가 필요한가?
- **프로젝트 오너십**: 백엔드 + iOS + Android + 웹 + 보안팀이 모두 관여하는 작업이다. 누가 단일 PM owner인가? 각 클라이언트팀의 스프린트 일정이 어떻게 정렬되는가?
- **A/B 테스트 가능 여부**: returnURL 보존 그룹 vs 기존 홈 리다이렉트 그룹으로 A/B 테스트가 가능한가? 가능하다면 효과 측정의 신뢰도가 크게 올라간다.
