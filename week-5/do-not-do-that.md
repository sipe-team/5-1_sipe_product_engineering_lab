# 5주차 PRD v2: 린다이어트 "후기/팁" 탭 콘텐츠 활성화 (기록 데이터의 C2C 재활용)

> **한 줄 요약**: GNB "후기/팁" 탭을 회사 블로그·광고 유튜브가 채우던 자리에서, 유저가 쓴 콘텐츠와 기록 데이터 기반 정보가 도는 자리로 바꾼다. 지금 탭은 사실상 100% 톱다운이다.

## 분석 대상

- **서비스**: 린다이어트 (자사 B2B2C 한약 다이어트 앱)
- **선정한 페인포인트**: 기록 데이터가 사용자 → 원장 방향으로만 흐르고, 사용자 쪽으로 되돌아오는 통로가 없다. 그 결과가 지금의 "후기/팁" 탭이다.

### 3주차 검증과의 연결

3주차에서 "AI 칼로리 대기 시간"을 검증했더니 임팩트가 낮았다(ICE 36). 대신 그 과정에서 **기록 데이터(+31pp 식사기록 품질, +12% 원장 차트 열람)가 사용자 → 원장 방향으로만 흐르고 사용자에게는 돌아오지 않는다**는 인사이트를 얻었다.

---

## 1. 배경 및 문제 정의 (Why)

### 문제 상황

린다이어트 GNB 5개 중 하나인 "후기/팁" 탭의 하위 카테고리:

| 카테고리        | 생산자      | 사용자 관점 |
| --------------- | ----------- | ----------- |
| 전체글          | 운영팀 통합 | 메타 피드   |
| 실제 후기       | 운영팀      | 톱다운      |
| 한의사 이야기   | 회사        | 톱다운      |
| 연구 일지       | 운영팀      | 톱다운      |
| 다이어트 궁금증 | 운영팀      | 톱다운      |
| 린다이어트팀    | 운영팀      | 톱다운      |

6개 카테고리 전부 운영팀이 쓴다. 이름이 "실제 후기"인 것조차 유저가 쓴 글이 아니라 연예인 VLOG다. 유저가 직접 쓴 글은 하나도 없다. "후기/팁"이라는 이름과 다르게, 사실상 회사의 방송 채널이다.

### 영향받는 사용자

친구 소개로 한의원에 갔다가, 원내 데스크 안내를 받고 앱을 설치한 **40/50대 여성 신규 사용자**.

### 근거

- 앱스토어 리뷰 2,215개 중 "후기/팁 탭 도움 안 된다"는 직접 언급은 없다. 불만으로 올라올 만큼의 기대치 자체가 없는 상태.
- 탭 체류·재방문을 볼 수 있는 이벤트 자체가 거의 심어져 있지 않다. 여태 린다팀의 관심사가 아니었다는 뜻.
- GNB 5개 중 1개라는 비싼 자리를 주고도 올라오는 콘텐츠는 방송 톤. 전략과 실제가 어긋나 있다.

### 방치하면

- GNB 자리 하나를 계속 낭비
- "기록만 하는 앱"이라는 인상이 굳어짐 → 프로그램 이탈로 이어짐
- 기록 데이터가 유저 쪽으로 돌아오는 루프가 영영 안 생김

## 2. 목표와 성공 지표 (What + KPI)

### 목표

> "후기/팁" 탭을 회사 방송 채널에서 유저 참여 창구로 바꾼다. 기록 데이터가 앱 안에서 유저 → 유저 방향으로 한 바퀴 도는 첫 씨앗을 심는다.

### KPI

| 지표                  | 카테고리   | 목표   |
| --------------------- | ---------- | ------ |
| 탭 평균 체류 시간     | Engagement | 60초+  |
| 탭 D7 재방문율        | Retention  | + X pp |
| 신규 1주 내 첫 진입률 | Adoption   | + X pp |

**숫자 근거 보강 (v2)**: v1에서 "~90초 / +15pp / +20pp"로 적었는데, 셀프 리뷰하면서 90초가 왜 90초인지 답할 수 없다는 걸 깨달았다. v2에서는 체류만 "짧은 후기 한 편을 끝까지 읽는 최소 시간 60초"로 보수적으로 내렸고, 나머지 두 개는 절대값을 비워뒀다. 베이스라인이 나온 뒤에 채워야할 것 같다.

**핵심 지표**: 체류 시간. 잠깐 열었다 나간 경우를 걸러내려고 D7 재방문율을 같이 본다.

**베이스라인 부재 (v2 수정)**: v1에서 "MVP 만들면서 같이 심으면 된다"고 적었는데, 그건 "MVP 종료 시점에 변화량을 측정할 방법이 없다"는 뜻이었다. 변화량을 보려면 변화 전 숫자가 있어야 한다. v2에서는 **베이스라인 측정을 MVP에서 분리해 Phase 0으로 선행**한다. 이벤트만 1~2주 먼저 심어 베이스라인을 잡고, 그 위에 본 MVP를 올린다.

## 3. 사용자 경험 변화 (Before → After)

**페르소나**: 김영자씨.., 52세, 카페 자영업. 친구 소개로 한의원에 갔다가 앱 설치.

### Before

"후기/팁" 탭을 열어본다 → 상단에 한의사 칼럼·연구 일지·FAQ → "대사" 같은 단어에서 막혀서 탭을 나간다 → 이후 3개월간 다시 안 연다.

### After (수집 플로우가 돌기 시작한 뒤)

"후기/팁" 탭을 열어본다 → 상단에 **같은 시기 시작한 N명·감량 구간 정보** + **비슷한 나이대 다른 유저가 쓴 후기** → 내려가면서 기존 카테고리도 본다 → 한 달 뒤 주 2~3회 들어오고, 한 달 반 뒤 본인도 앱에서 뜬 작성 프롬프트로 후기 한 줄을 남긴다.

> _카테고리 문구·섹션 이름은 예시. 실제 UI 라벨은 UX 라이팅 단계에서 결정. MVP 직후에는 유저 후기가 아직 수집 중이라 데이터 카테고리부터 뜨고, 시드 후기가 모이면서 UGC가 순차적으로 채워진다._

## 4. 솔루션 접근법 (How 개괄)

### 3개 축

1. **유저가 쓴 콘텐츠 (UGC 0→1)**
   - 지금 탭에 유저 후기가 하나도 없어서 0부터 시작해야 한다
   - 앱 안에 후기 작성 프롬프트를 두고, 프로그램 N주차 시점에 띄운다
   - 초기 시드는 운영팀·CS팀이 유저에게 직접 요청해서 확보하는 경로도 열어둔다
   - 모수가 쌓이면 나이·시작 시점 기준으로 자동 큐레이션으로 넘어간다

2. **기록 데이터 기반 집단 정보**
   - 같은 시기 시작한 동료 수·감량 구간 같은 집단 통계를 카테고리로 보여준다
   - 프라이버시 가드레일: N≥20 / 구간화 / 고지문 / 유저 토글
   - 유저 후기가 쌓이기 전에는 이 카테고리가 탭 상단의 주 콘텐츠 역할을 한다

3. **유저 간 상호작용 씨앗 (V2 이후)**
   - 공감 버튼 → 댓글 → 그룹 피드 순으로 단계적으로 늘려간다
   - MVP에는 안 넣지만, 나중에 올릴 수 있도록 초기 데이터 스키마 단계에서 감안한다

### 기술 고려사항

- **UGC 수집 플로우**: 작성 프롬프트 트리거, 작성 UI, 작성 후 집계 파이프라인
- **모더레이션**: 처음엔 운영팀 수동 리뷰 + 유저 신고 버튼
- **측정 인프라**: 탭 체류·클릭·재방문·후기 작성 이벤트 같이 심기 (Phase 0으로 선행)
- **A/B 테스트**: 신규와 기존 사용자 분리

### A 점수 한 줄 근거 (v2 보강)

v1에서는 점수만 적고 근거를 안 적었다. 셀프 리뷰하면서 보니 "그냥 8점 같아서"가 되어버린 걸 발견했다.

- **Impact 8**: 영향받는 모수는 "GNB 5개 중 1개 탭에 진입할 수 있는 전체 액티브 유저". 일단 GNB 진입 가능 유저 전체이지만, 실제 진입 유저들이 있는지는 데이터를 확인해봐야함.
- **Confidence 6**: UGC 0→1 패턴은 다이어트 도메인에서 검증된 사례를 직접 찾기 어렵다(아래 벤치마킹 참고). 가장 큰 불확실성은 "40/50대 여성이 후기를 쓰겠는가". 그래서 6점. 강남언니 사례로 7까지 올릴 여지는 있다.
- **Ease 4**: 수집 플로우·노출·측정 인프라를 같이 만들어야 했던 v1 MVP 기준 4점. v2에서 MVP를 "데이터 카테고리 1개"로 줄였으니 6~7점으로 올라가야 맞지만, 점수를 다시 매기는 대신 범위 섹션에서 실행 단위를 잘게 쪼개는 방식으로 풀었다.

### 선택 근거

점수만 보면 B(294)가 A(192)보다 높지만 A로 간다. B는 "데이터 카테고리만 보여줘도 체류가 움직이는가"라는 좁은 질문에만 답하고, A는 "데이터와 유저 후기가 함께 있을 때 작동하는가"라는 이번 PRD의 진짜 질문에 답한다. 린다이어트 탭에 UGC가 0%인 상황에서는, 수집 플로우를 만드는 작업 자체가 이 PRD가 가려는 방향의 핵심 실험이다.

**v2에서 한 발 더**: 셀프 리뷰하면서 보니, A를 골랐다는 게 "한 스프린트에 다 한다"를 뜻하면 안 됐다. v2에서 A를 두 개의 가설(H1/H2)로 쪼개서 MVP는 H1만 답하고 H2는 V1에서 답하도록 분리. A를 고른 이유는 그대로 살리되, 실행 단위를 잘게 쪼갠 것이다(아래 범위 섹션 참고).

리소스가 정말 빠듯하거나 UGC 수집 플로우 설계가 막히면 **B로 축소**. 데이터 카테고리만 먼저 내고 UGC 수집은 V1으로 미룬다. (사실 v2의 Phase 1이 이미 B에 가깝다.)

**D (인센티브)**: 처음에는 인센티브 없이 프롬프트만으로 시작하되, 2주간 수집률이 기대 이하면 V1에서 바로 도입한다.

## 6. 범위와 우선순위 (Scope)

### MVP가 답할 가설 분리 (v2 추가)

v1에서 MVP를 4개 항목(수집·노출·시드·측정)으로 묶고 "한 스프린트에 다 같이 돌아야 한다"고 변호했다. 셀프 리뷰하면서 보니 그건 한 사람이 한 스프린트에 4개를 동시에 본다는 뜻이고, 리소스(Mobile 1 / BE 1 / 디자이너 1 / 기획 1, 전원 병렬)와 정면 충돌이었다.

가설을 두 개로 쪼갰다.

- **H1 (MVP에서 답한다)**: 데이터 카테고리만 추가해도 탭 체류·재방문이 움직이는가?
- **H2 (V1에서 답한다)**: 데이터 카테고리에 UGC 후기가 합쳐지면 더 움직이는가?

H1만 답해도 "기록 데이터가 사용자에게 돌아오는 통로"의 첫 검증이 된다. 안 움직이면 H2로 안 간다. 움직이면 그 위에 H2를 쌓는다.

### 단계 구성

| 범위               | 내용                                                                                              | 우선순위 층위         |
| ------------------ | ------------------------------------------------------------------------------------------------- | --------------------- |
| **Phase 0 (선행)** | 탭 체류·클릭·재방문 이벤트만 심기. 1~2주간 베이스라인 확보.                                       | Must (선행)           |
| **MVP (Phase 1)**  | 집단 통계 카테고리 1개(동료 수 or 감량 구간) 노출. **H1 검증**.                                   | Must                  |
| **V1 (Phase 2)**   | UGC 수집 플로우(작성 프롬프트 + 작성 UI + 집계 파이프라인). 시드 후기 단계적 노출. **H2 검증**.   | Should                |
| **V1 후속**        | 집단 통계 카테고리 2개로 확장. UGC 큐레이션 다듬기. 통계 참여 토글. 수집률 부진 시 인센티브 도입. | Should                |
| **V2**             | 후기 공감 버튼. 반응 카운트                                                                       | Could (커뮤니티 씨드) |
| **V3**             | 댓글·답글. 기간 기반 그룹 피드. 탭 전면 리뉴얼. 원장 B2B 확장                                     | Could (장기)          |
| **Out of Scope**   | 광고 유튜버 콘텐츠 즉시 제거, AI 대기 시간, 홈 영양소 노출, 탭 이름 변경, 본격 커뮤니티 기능      | Won't                 |

**MVP를 1개로 줄인 이유 (v2)**: v1의 변호는 "수집·노출·측정이 모두 같이 돌아야"였는데, 그 말은 곧 "H1과 H2를 합쳐서 검증하겠다"였다. 이러면 체류가 안 움직였을 때 카테고리 때문인지 UGC 부재 때문인지 구분이 안 된다. 첫 가설은 좁아야 답이 명확하다. UGC 수집은 H1이 검증된 뒤에 V1에서 본격적으로 도입한다.

## 7. 리스크

### 1. 프라이버시 역추론 (법률·데이터팀 우려)

- **시나리오**: 모수가 작을 때 감량 구간을 보여주면 역추론 가능. 사용자가 "내 기록이 나오는 거 아닌가?" 하는 순간 기록 자체를 안 하게 된다. 핵심 루프가 무너질 수 있다... 안돼...
- **완화**: N≥20 / 구간화 / 고지문 / 참여 토글 / 법률팀 사전 리뷰 / 데이터팀 기술 감수

### 2. UGC 수집 실패 (가장 큰 불확실성)

- **시나리오**: 수집 플로우를 만들어도 환자가 후기를 안 쓰면 이 가설을 확인할 방법이 없다. UGC 카테고리가 영영 빈 채로 남는다.
- **완화**:
  - 별도의 추가 플로우 없이, 현재 수집되고 있는 한의원 만족도 조사로 확보
  - 위 데이터가 빈약할 경우, 인센티브 도입도 고려해볼 수 있음

### 3. 집단 수치·유저 후기가 사용자에게 압박이 되는 경우

- **시나리오**: 평균보다 낮은 자기를 보고 좌절해서 기록을 접는다. 40/50대는 이런 비교에 특히 민감할 수 있다.
- **완화**: 숫자 대신 구간 노출 / 시작 시점 기준으로 비교 / 성공 사례만 뽑지 않기 / 기록 중단율을 가드 지표로 모니터링

### 4. UGC 편향·조작 (수집 시작 후 나타남)

- **시나리오**: 긍정 후기만 올라오면 광고처럼 읽힌다. 초기 시드로 운영팀이 받아온 후기도 특정 성향으로 기울 수 있다.
- **완화**: 세그먼트 필터만 적용(품질 점수 매기지 않음) / 부정 후기도 허용하는 정책 / 초기 시드 요청 시 가이드 문구는 중립 / 유저 신고 버튼은 MVP에 포함

## 8. 열린 질문

v1에서는 12개를 나열만 했다. 셀프 리뷰하면서 보니 "모르겠다"의 나열로는 부족했다. 각 질문 옆에 답을 얻는 방법을 같이 적어야 정직한 PRD가 된다.

## 벤치마킹 (5주차 추가)

### 솔루션 한 문장 정리

> 기록 데이터의 집단 통계를 유저에게 되돌려주고, UGC 후기를 시드 확보부터 시작해 단계적으로 키우는 패턴.

이 패턴을 두 축으로 쪼갰다. **(A) 의료 도메인에서 후기 시드 확보**, **(B) 집단 통계로 동기 부여**. 각 축마다 참고 서비스 한 개씩 뒀다.

### 참고 서비스 1: 강남언니 — 의료 도메인 후기 시드

- **어떻게 풀었는지**: 시술 후기 카테고리에 진입했을 때 운영팀이 직접 확보한 시드 후기가 상단을 채웠고, 후기 작성에 캐시 인센티브를 붙여 모수를 빠르게 키웠다. 검수는 명단 기반으로 운영팀 수동 모더레이션.
- **반영할 점**: 의료 도메인에서 40/50대 여성 사용자가 후기를 쓰는 데 심리적 허들이 있다는 가정이 우리 페르소나(김영자님)와 동일. 운영팀 시드 + 인센티브 조합이 실제로 작동했다는 점이 ICE A안의 Confidence를 6 → 7로 올릴 근거가 된다. 우리 PRD의 "초기 시드는 운영팀·CS팀이 확보" 전략에 직접 매핑.
- **차별화할 점**: 강남언니는 후기가 "구매 결정 정보"라 작성 동기가 강하지만, 우리 후기는 "동료 응원" 성격이라 동기 구조가 다르다. 인센티브 의존도를 더 높게 잡거나, 후기 자체의 "응원 받는 경험"을 더 명확히 설계해야 한다.

### 벤치마킹 소스를 더 못 찾은 이유

다이어트 도메인에서 "기록 데이터를 유저에게 돌려주는" 사례를 직접 찾기는 어려웠다. 핏빗·애플워치 등 헬스 트래커는 개인 통계 위주이고, 다이어트 앱(MyFitnessPal 등)은 톱다운 콘텐츠 위주여서 우리 패턴과는 다르다. **이게 의미 있는 결론이기도 하다 — 같은 패턴을 쓴 다이어트 앱이 없다는 건 우리가 처음 검증해야 할 영역이라는 뜻**이고, ICE Confidence 6의 가장 큰 이유다.

## v1 → v2 변경 사항 (5주차 추가)

### 셀프 리뷰에서 발견한 구멍

1. **MVP 범위가 V2 수준이었음** — v1에서 MVP를 4개 항목(수집·노출·시드·측정)으로 묶고 "한 스프린트에 같이 돌아야" 한다고 변호했는데, 리소스 섹션과 정면 충돌이었다. v2에서 MVP를 "데이터 카테고리 1개"만 남기고, 베이스라인은 Phase 0으로 분리, UGC는 V1으로 미뤘다. 가설도 H1/H2로 쪼개서 MVP가 답할 질문을 좁혔다.

2. **성공 지표에 베이스라인이 없었음** — "탭 체류 이벤트가 없어서 MVP 만들면서 심으면 된다"고 적었는데, 그 말은 곧 "변화량 측정 방법이 없다"였다. v2에서 Phase 0(베이스라인 측정)을 MVP에서 분리하고, KPI 절대값(+15pp 같은)은 베이스라인이 나온 뒤 채우기로 변경했다.

3. **ICE 점수에 한 줄 근거가 없었음** — A안의 8/6/4가 왜 그 점수인지 답할 수 없었다. v2에서 Impact/Confidence/Ease 각각 한 줄 근거 추가. Confidence 6은 벤치마킹으로 7까지 올라갈 여지를 같이 명시했다.

4. **열린 질문에 "어떻게 답을 얻을지"가 없었음** — 12개 질문이 있었지만 답을 얻는 방법이 없으면 모르겠다의 나열에 그친다. v2에서 각 질문 옆에 검증 방법(인터뷰·법률 검토·Phase 0 데이터·운영팀 미팅)을 명시했다.

### 벤치마킹으로 강화한 부분

- 강남언니의 "시드 후기 + 인센티브" 사례를 근거로, A안 Confidence 6 → 7로 올릴 여지 확보 (실제 점수 변경은 직접 사용 후 확정).
- 강남언니에서 "운영팀의 역할이 콘텐츠 작성 → 시드 확보·모더레이션으로 옮겨가는 패턴"을 확인했지만, 이번 v2에서는 본인 회사의 "한의원 만족도 조사 데이터 활용"이 더 현실적인 경로라고 판단해서 그쪽으로 완화 방안을 바꿈. 강남언니는 "그래도 작동했다는 선례"의 역할로만 남김.

### 그대로 둔 부분 (셀프 리뷰 통과)

- Before/After 섹션 (김영자님 페르소나를 끝까지 끌고 가는 서술)
- 핵심 4개 리스크의 시나리오·완화 톤 (프라이버시·UGC 수집·심리 압박·편향) — 개수는 줄였지만 남긴 것의 구조 자체는 v1에서 가져왔다
- 문제 정의 섹션 (한 문장으로 말할 수 있고, 데이터 근거도 인용되어 있음)

### 다음(6주차 발표) 단계에서 정리할 것

- v1 → v2의 의사결정 변화 자체가 발표 소재. 특히 "MVP가 4개 → 1개로 줄어든 이유"는 셀프 리뷰의 가장 큰 학습 포인트.
- 강남언니 직접 써보고 벤치마킹 보강 후, ICE Confidence 점수 확정. 추가 후보가 필요해지면 그때 한 개 더.
- Phase 0 베이스라인 측정 결과가 있으면 KPI 절대값(+X pp) 채우기. 없으면 "Phase 0 종료 후 확정"으로 명시.
