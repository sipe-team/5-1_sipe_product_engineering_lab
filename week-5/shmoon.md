# 5주차: PRD v2 — 공시·실적 요약 카드 Chrome Extension "DARTshot"

> **한 줄 요약**: 개인 투자자가 네이버 금융 종목 페이지에서 PDF나 DART 사이트 이동 없이, Extension이 자동으로 DART 공시와 분기 실적을 30초 안에 카드로 보여준다.

> **v1 → v2 변경 핵심**: v1은 네이버 금융 내부 기능 개선 제안(증권사 PDF 파싱)이었으나, 저작권·계약 리스크와 내부 승인 불필요성을 고려해 **독립 Chrome Extension 서비스**로 전환. 데이터 소스도 증권사 PDF(회색지대) → DART OpenAPI(공식 무료)로 교체.

## 분석 대상

- **서비스**: DARTshot (신규 Chrome Extension)
- **해결하는 페인포인트**: 개인 투자자가 종목 분석 시 공시·실적 확인을 위해 DART 사이트, 네이버 금융, 증권사 앱을 오가며 겪는 정보 수집 비용 과다

## v1 회고 및 변경 이유

### v1에서 잘 정의된 것
- 문제 정의: "PDF 없이 30초 안에 핵심 파악" — 여전히 유효
- Before/After 시나리오: 박민준의 PDF 탐색 → 이탈 흐름
- ICE Score 구조와 Scope 분리 방식

### v1의 핵심 약점 (피드백 반영)
1. **저작권 리스크 과소평가**: PDF 파싱 행위 자체가 저작권법·계약 위반 가능성. MVP 전제조건으로 법무 검토가 필요한 구조는 실행 가능성이 낮음
2. **네이버 내부 의존**: 네이버가 만들어야 하는 기능이라 외부에서 가설 검증 불가
3. **KPI 측정 불가**: "PDF 미클릭 이탈률"은 네이버 내부 데이터 없이 측정 불가

### v2 전환 논리
> 같은 문제(정보 접근 비용 과다)를 **저작권 리스크 0, 직접 측정 가능한 KPI, 즉시 구현 가능**한 방식으로 푼다.

## 1. 배경 및 문제 정의 (Why)

### 문제 상황

개인 투자자가 종목 투자 결정 전 거치는 정보 수집 루틴:

```
네이버 금융 종목 검색
→ 실적 확인하러 DART 이동 (사이트 전환 1)
→ 기업 코드 검색 → 사업보고서 찾기 → PDF 열기
→ 공시 확인하러 다시 DART 메인 (사이트 전환 2)
→ 종목명으로 공시 검색 → 원문 확인
→ 다시 네이버 금융으로 복귀
```

이 루틴에서 발생하는 비용:
1. **탭 전환 비용**: 평균 3~5개 탭을 오가며 정보 수집
2. **DART UX 난이도**: DART 사이트는 기업 코드 기반 검색 구조라 종목명으로 바로 찾기 어려움
3. **공시 해석 비용**: 원문이 길고 어디가 핵심인지 파악하기 어려움
4. **실시간성 부재**: 공시가 올라와도 투자자가 능동적으로 확인하지 않으면 인지 불가

### 영향받는 사용자

- **핵심 타겟**: 네이버 금융을 주 정보 수집 채널로 쓰는 개인 투자자
- **세그먼트**: 투자 경험 1년 이상, 실적 발표 시즌에 주 3회 이상 종목 페이지 방문
- **규모 추정**: 네이버 금융 월간 방문자 약 1,500만 명 중 실적·공시 탭 진입 사용자 추정 10~15% → 약 150~225만 명

### 근거

**앱 리뷰·커뮤니티 분석 (v1 3주차 인용)**:
- "DART 들어가서 찾는 게 너무 복잡해서 결국 유튜브로 대체한다"
- "실적 발표 날 공시 뜨는 거 바로 알고 싶은데 방법이 없다"

**벤치마킹 — 유사 서비스 현황**:

| 서비스 | 국가 | 핵심 기능 | 한계 |
|--------|------|-----------|------|
| [DART Feed](https://chromewebstore.google.com/detail/dart-feed/hmgomhokiihomekcbcfgileibikhdndk) | 한국 | 공시 알림 Extension | 실적 분석 없음, 단순 목록 표시 |
| [MoneySense AI](https://moneysense.ai) | 미국 | SEC 공시 AI 분석 | 한국 DART 미지원 |
| [Corporate Action Tracker](https://chromewebstore.google.com/detail/corporate-action-tracker/onanoffjjooamaoiopaailimimpggfaj) | 미국 | 배당·합병 추적 | 실적 서프라이즈 감지 없음 |
| [Blueflame AI](https://www.blueflame.ai) | 미국 | 실적 발표문 AI 요약 | 한국 시장 미지원, 유료 |
| OpenDartReader | 한국 | DART API Python 라이브러리 | 브라우저 Extension 아님, 개발자용 |

**결론**: 한국 DART 기반으로 **실적 분석 + 공시 분류 + 네이버 금융 연동**을 동시에 제공하는 Extension은 현재 존재하지 않음. 명확한 공백.

### 방치하면 생기는 비즈니스 영향 (서비스 관점)

- 정보 수집 비용이 높은 개인 투자자는 유료 서비스(FnGuide, 에프앤가이드 등)로 이탈
- 실적 발표 직후 정보 격차 → 개인 투자자의 의사결정 품질 저하
- 한국판 Bloomberg Terminal 수준의 정보를 무료로 제공하는 서비스 공백 지속

> 개인 투자자가 네이버 금융 종목 페이지에서 탭 전환 없이 30초 안에 최근 실적 트렌드와 주요 공시를 파악할 수 있게 한다.

### 성공 지표 (KPI)

| 지표 | 카테고리 | 현재 | 목표 (출시 4주 후) |
|------|---------|------|------------------|
| Chrome Web Store 설치 수 | Adoption | 0 | 500+ |
| DAU / 설치 수 비율 (활성률) | Retention | - | 30% 이상 |
| 세션당 카드 조회 수 | Engagement | - | 평균 3개 이상 |

## 3. 사용자 경험 변화 (Before → After)

### Before (현재)

박민준(32세, 직장인 투자자)은 삼성전자 실적 발표 다음 날 네이버 금융에서 삼성전자를 검색한다.

실적이 궁금하다. 종목 페이지에서 실적 수치를 찾는다. 분기 매출·영업이익은 있지만 전년 동기 대비 증감률이 없다. "직접 계산해야 하나?" DART로 이동한다. DART 메인에서 삼성전자를 검색한다. 기업 코드가 필요하다. 다시 찾는다. 사업보고서를 연다. 100페이지짜리 PDF다. Ctrl+F로 "영업이익"을 검색한다. 숫자를 찾아 지난 분기와 비교한다.

공시도 확인하고 싶다. DART에서 최근 공시 목록을 본다. 10개 중 뭐가 중요한지 모른다. "주요사항보고서"를 클릭한다. 원문을 읽는다. 5분이 지났다.

박민준은 결국 유튜브에서 "삼성전자 실적 정리" 영상을 찾아본다.

박민준은 네이버 금융에서 삼성전자를 검색한다. 종목 페이지 우측에 DARTshot 카드가 자동으로 펼쳐진다.

## 4. 솔루션 접근법 (How - 개괄)

### 접근 방식

> **DART OpenAPI(무료·공식)로 실적·공시 데이터를 가져와, 네이버 금융 종목 페이지에 카드 UI를 인젝션한다. 저작권 리스크 0, 네이버 내부 승인 불필요.**

### 핵심 아이디어

1. **실적 카드**: DART `fnlttSinglAcntAll` API로 최근 4분기 재무 데이터 → 매출·영업이익·증감률·컨센서스 대비 서프라이즈 자동 계산
2. **공시 카드**: DART `list` API로 최신 공시 3~5개 → 공시 유형별 호재/중립/모니터링 분류 (규칙 기반)
3. **네이버 금융 연동**: 종목 페이지 URL의 종목코드 추출 → DART 기업코드 매핑 테이블로 자동 연결
4. **원문 직행 링크**: 공시 카드 클릭 시 DART 원문 URL로 직행 (DART 트래픽 기여, 협력 관계)

### 기술 스택

```
Chrome Extension (Manifest V3)
├── content_script.js  — 네이버 금융 DOM 감지 + 카드 인젝션
├── background.js      — DART API 호출 (CORS 우회)
├── dart_mapper.js     — 종목코드 ↔ DART 기업코드 매핑
└── card_ui.css        — 카드 스타일링
```

- **DART OpenAPI**: 무료, API 키 발급만으로 사용 가능
- **컨센서스 데이터**: 초기엔 네이버 금융 DOM에서 컨센서스 수치 파싱 (선택적)
- **공시 분류**: 규칙 기반(공시 유형 코드 매핑)으로 시작, 이후 Claude API 연동으로 자연어 요약

### 기술적 고려사항

- **CORS**: DART API는 브라우저 직접 호출 시 CORS 에러 → `background.js`에서 `fetch` 처리
- **매핑 테이블**: 코스피·코스닥 전 종목 기업코드 매핑 JSON (DART에서 일괄 다운로드 가능)
- **캐싱**: 동일 종목 반복 방문 시 API 재호출 방지 → `chrome.storage.session` 활용
- **업데이트 주기**: 실적은 분기별, 공시는 실시간(페이지 방문 시마다 호출)

### 선택한 아이디어

**A + B를 MVP로 함께 채택한다.**

- **A-Impact 9**: 실적 증감률은 투자자가 가장 먼저 확인하는 정보. 이걸 자동 계산해서 보여주는 것만으로도 탭 전환 3~4회를 대체.
- **A-Confidence 8**: DART `fnlttSinglAcntAll` API가 정형화된 재무 데이터를 JSON으로 제공. 파싱 실패 리스크 거의 없음.
- **A-Ease 7**: API 호출 + 증감률 계산 + 카드 렌더링. 복잡한 로직 없음.
- **B-Impact 8**: 공시는 실적보다 더 실시간성이 중요. 오늘 올라온 공시를 종목 페이지에서 바로 보는 것 자체가 차별점.
- **B-Confidence 7**: 공시 유형 코드(예: A001=사업보고서, C001=자기주식취득)가 DART에 정의되어 있어 규칙 기반 분류 가능. 단, 분류 정확도는 검증 필요.
- **B-Ease 7**: `list` API + 유형 코드 매핑 테이블. A보다 단순.

### 선택하지 않은 아이디어

- **C (서프라이즈 감지)**: 컨센서스 데이터를 안정적으로 가져올 소스가 불확실. 네이버 금융 DOM 파싱에 의존하면 구조 변경 시 깨짐. V1에서 소스 확정 후 추가.
- **D (자연어 요약)**: Claude API 호출 비용 + 레이턴시 이슈. MVP에서는 규칙 기반으로 시작하고 V1에서 붙임.
- **E (목표주가 컨센서스)**: 증권사 리포트 데이터 소스 문제(v1의 저작권 이슈 재발). 보류.

## 7. 리스크와 대안 (Risks)

### 리스크 1: 네이버 금융 DOM 구조 변경

- **시나리오**: 네이버가 종목 페이지 UI를 개편하면 카드 인젝션 위치가 깨짐.
- **완화**: 특정 클래스명 의존 대신 URL 패턴(`finance.naver.com/item/main.nhn?code=`) + 종목코드 추출 방식으로 구현. DOM 변경 감지 로직 추가. 깨졌을 때 카드가 안 보이는 것으로 폴백(기존 페이지에 영향 없음).

### 리스크 2: DART API 호출 한도

- **시나리오**: DART OpenAPI는 일 10,000건 호출 제한. 사용자가 늘면 공유 API 키 사용 불가.
- **완화**: 사용자별 API 키 입력 방식(Extension 설정 화면). 캐싱으로 불필요한 재호출 방지. V1에서 프록시 서버 도입 검토.

### 리스크 3: 공시 분류 오류로 신뢰도 하락

- **시나리오**: 규칙 기반 분류가 맥락을 놓쳐 "호재"로 표시된 공시가 실제로 악재인 경우 → 투자 판단 오류 유발.
- **완화**: MVP에서는 분류를 "단순 유형 레이블"로만 표시(예: "자기주식 취득", "유상증자"). 호재/악재 판단은 V1 자연어 요약 도입 후에만 적용. 항상 "원문 확인 권장" 문구 + 원문 링크 노출.

### 리스크 4: Chrome Web Store 정책 위반

- **시나리오**: 금융 정보 표시 Extension이 스토어 금융 서비스 정책에 걸릴 수 있음.
- **완화**: "투자 조언 아님, 정보 제공 목적" 면책 문구 명시. 매수/매도 추천 기능 Out of Scope. MVP는 로컬 로드로 먼저 검증 후 스토어 제출.

**참고 자료 감상평:**

[PRD 중심으로 AI 에이전트와 제품 개발하기 — yozm](https://yozm.wishket.com/magazine/detail/3221/)

> v1 PRD를 다시 읽으면서 "누가, 왜, 어떻게 제품을 사용해 어떤 가치를 가져갈 것인가"라는 질문이 충분히 답해지지 않았다는 걸 깨달았다. v1은 네이버 금융이 만들어야 하는 기능을 제안하는 형태였는데, 실제 사용자(박민준)가 이 기능을 어떻게 발견하고 쓰게 되는지의 경로가 모호했다. v2에서 Chrome Extension으로 전환한 것은 "사용자가 직접 설치하고 즉시 가치를 경험한다"는 더 명확한 사용 경로를 만든 결과다. PRD를 "팀이 함께 맞추는 기준점"으로 본다면, v2가 훨씬 더 엔지니어와 디자이너가 바로 논의를 시작할 수 있는 문서에 가깝다.
